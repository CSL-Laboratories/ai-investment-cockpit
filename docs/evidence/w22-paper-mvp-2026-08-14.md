## 12:02 PT follow-up — false audit failure under a concurrent WAL commit

The paper-performance minute tick emitted `watch_only` with `audit chain verification failed`
at 19:02:06 UTC and recovered at the next tick, without database repair. The surrounding signed
ledger makes the concurrency explicit:

- sequence 2,878: Alpaca portfolio snapshot;
- sequence 2,879: market-data raw snapshot;
- sequence 2,880: paper-performance `watch_only` alert;
- sequences 2,881–2,891: ingest batch plus ten more market-data snapshots;
- sequence 2,892: next Alpaca portfolio snapshot;
- sequence 2,893: paper-performance recovery.

The chain subsequently verified through a later head with a matching signed high-water. Root
cause was `BUG-104`, not HMAC corruption: under Python 3.11 sqlite3 legacy transaction control,
the verifier's ledger-row `SELECT` and audit-meta `SELECT` were separate WAL snapshots. A commit
between them could expose rows through head N and the atomically committed watermark at N+1,
which resembled truncation for one tick.

The verifier now explicitly pins both reads to one SQLite read transaction and linearizes its
in-process erasure floor at the start of that snapshot. A deterministic attack regression forces
a valid append between the two reads: the in-flight verification accepts the valid N snapshot,
and the next verification accepts N+1. Existing regressions still reject a sequence gap, wrong
HMAC, edited timestamp, invalid/missing watermark, tail truncation, and total in-process erasure.
Paper-performance alerts now include the verifier's specific integrity error rather than the
generic failure string.

The complete local Windows gate passed after the repair: 2,186 passed / 1 skipped, five known
dependency deprecation warnings, Ruff clean, and `git diff --check` clean. This event means the
pre-fix portion of 2026-08-14 is diagnostic evidence, not a qualifying unattended W-22 day.

# Verified-ancestor CI cancellation

CSL-255 owner approval on 2026-10-16 retains one ordinary PR concurrency group per workflow and draft state. Ordinary PR runs use `cancel-in-progress: false` and `queue: max`: a delayed synchronize event cannot evict a newer head from the running or pending slot. Label, manual, nightly, push and merge-group policies retain their existing groups and cancellation behavior. Required status names are unchanged.

The existing `ci-label-retrigger.yml` companion also handles `workflow_run` requested/completed events for `ci` and `rust`. This event runs from the default branch. It checks out only the default-branch controller policy, never PR code or artifacts, using the companion's existing Actions-write, contents-read and pull-requests-read permissions. Controller invocations have separate groups; label dispatch retains head and scope isolation.

Before requesting ordinary-run cancellation, `scripts/ci/ci_cancel_controller.py` verifies the numeric repository/workflow/run/PR identities, exact allowlisted workflow paths, same-repository head/base branches, one exact PR association, and the live open/non-draft PR. Each workflow needs an actual eligible run at that live head. A completed cancelled/failed newest run is not replaced by an older success; any current-head rerun suppresses cleanup because run IDs cannot order attempts across different runs. The controller never reruns or marks a check successful.

Only an active run whose SHA is a proven strict ancestor of the live head is eligible. A different SHA or older timestamp is insufficient. Discovery reads both complete workflow snapshots before any write. Before each cancellation it refreshes the current-head witness selection, rechecks both run identities/attempts, repeats the ancestry proof, and finally reads the live PR again. Missing, ambiguous, capped, duplicate, changing or failed API evidence stops cleanup. Reads are uncached; the controller uses at most 160 API calls and 120 seconds, with at most 10 seconds per request, and refuses listings of 1,000 or more runs. Cancellation responses are reported as requests, not proof of terminal cancellation. Uncertain writes are never retried.

This is a bounded optimization, not an atomic transaction or a guarantee of cancellation or savings. A head or run status can change after the final read. Under fast-forward-only development, a verified ancestor remains obsolete when the head advances; an external force-reset or divergent rewrite in that final gap can break that property. Such history changes remain prohibited. Full snapshot equality can decline cleanup during normal status changes. Requested events do not cover reruns; completed events can offer another reconciliation opportunity but delivery, budget, pagination and state changes can still prevent cleanup. Human-cancelled current runs are not restarted. Stacked PRs and shared SHAs do not substitute for exact PR/branch identity.

Before the companion policy lands on the default branch, ordinary runs queue safely and execute without this optimization. A missing default-branch script produces an explicit bootstrap notice. The GitHub queue has a maximum of 100 pending runs; this policy does not promise unlimited admission. Forks, drafts, divergent histories and unavailable APIs receive no controller cancellation. No repository settings or permissions change is part of this rollout.

Validation uses `tools/test_ci_cancel_controller.py` and `tools/test_ci_dispatch_scope.py`: fake API executions cover stale arrival, head changes, cancelled successors, reruns, provenance, pagination, API errors, uncertain writes and bootstrap behavior. The actionlint queue-key exception is restricted to exact diagnostics for named workflow files, with executable negative controls. Offline tests do not prove hosted workflow admission; normal ordinary PR and full manual runs must validate both conditional queue branches after publication. No live cancellation or negative queue experiment is required or authorized by this change.

Primary references: [GitHub concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency), [workflow_run](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run), and the [official workflow schema](https://github.com/actions/languageservices/blob/main/workflow-parser/src/workflow-v1.0.json). The schema defines queue values `single` and `max` inside the concurrency expression context; hosted acceptance remains a rollout check.
